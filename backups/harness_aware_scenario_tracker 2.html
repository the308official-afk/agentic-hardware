Experiment Rule

For each scenario, start with two modes only: a baseline where the backend does not receive the harness signal, and a harness-aware controller mode where the backend uses the signal to make the smarter decision. Add diagnostic modes only when the two-mode story does not explain the result.

Before any new real experiment, coordinate with the backend task to reuse the established SGLang scripts, hooks, modes, and proof columns.

After every scenario run finishes, update this tracker with the latest result cards, a short interpretation, and links to the detailed report and proof files.

Scenario 1: Better Deadline Scheduling

Clear Win

A group of replay requests becomes ready at different times after tool waits. The harness exposes when each replay is expected to become ready, so the backend can move the soonest-due replay work forward instead of treating the workload as ordinary queue traffic.

In simple words: this scenario checks whether the backend can improve the whole replay workload when the harness tells it, "these tool calls will return at these times, and every replay wants its next token as soon as possible."

How the experiment is set up

The same 32 replay requests are run in both modes using the same generated timeline. Tool waits are sampled from realistic buckets, so some replays return quickly and others return much later. In baseline mode, replay submissions use ordinary FIFO behavior. In controller mode, the harness exposes replay timing during tool wait; the controller assigns due-time priority before replay, uses that priority in the local submission gate, and lowers the same priority into SGLang.

Scenario 2: Proactive KV-Cache Management

Improved + Guarantee Smoke

Many long-context sessions enter tool wait and are likely to resume at different times. The harness exposes each session's identity, reusable prefix, expected return time, reuse likelihood, and recompute cost, so the backend can prepare valuable KV before replay.

In simple words: this scenario checks whether the backend can prepare KV for all soon-returning replay sessions, not just one special target session.

How the experiment is set up

The same 32 replay requests are run in both modes using the same generated timeline. Each replay session has its own session_id and prefix_id. In baseline mode, the backend waits until replay arrives. In controller mode, the harness exposes ETA, reuse probability, and recompute cost during tool wait. The controller requests real SGLang-side KV preparation only when the window is safe enough for the load to finish before replay.

The full run shows a modest timing improvement while the controller refused all unsafe direct KV work. It is not a clean proof of proactive KV benefit because no direct load was admitted. The positive-path smoke run prepared_prefix_control_smoke4_20260917_044411 forced a long window and proved the real mechanism: SGLang prepared 5,168 tokens through hiradix.load_back+hicache.start_loading, and the target replay performed zero additional H2D/load-back events.

What we learned: the direct SGLang path now works, but the full experiment needs enough safe long-window opportunities to exercise it. For short or medium waits, the controller should skip direct KV work instead of competing with replay. For long waits, direct KV work can be admitted only if it completes before replay and the replay audit proves clean reuse.
Next tuning direction: run a full admission-positive Scenario 2 variant with guaranteed long windows, or relax the conservative contract after calibration. The current default is intentionally strict: long waits only and a 3x direct-load estimate multiplier.

Scenario 3: Better Cache Eviction Decisions.

In simple words: when memory is tight, the backend should avoid throwing away the KV that will be needed soon and would be expensive to rebuild. It should evict the less useful cache instead.

How the experiment is set up

Create two cached sessions: one target session that is likely to resume soon and has expensive KV, and one lower-value idle/background session. Add memory pressure so something must be evicted. Baseline eviction uses ordinary cache behavior. Controller mode uses reuse likelihood and recompute cost to protect the valuable target KV and evict the cheaper one.

In simple words: if the harness says a user-facing replay is about to return, the backend should leave enough GPU room for it at the right time, without wasting GPU capacity too early.

Scenario 5: Smarter Prefill Chunking.

In simple words: if a big background prefill is running and an urgent replay is coming soon, the backend should break the background work into smaller pieces so the urgent replay does not get stuck waiting.

How the experiment is set up

Start a large background prefill and schedule a target replay to become ready soon. In baseline mode, the background prefill uses large chunks, so the target may wait for a chunk boundary. In controller mode, the backend sees the replay ETA and shrinks background chunks near that time, creating faster interruption points for the target.

Scenario 7: Critical-Path Scheduling.

In simple words: if one request unlocks several other steps in the workflow, the backend should run that request before unrelated work, so the whole job finishes sooner.

How the experiment is set up

Make two similar-size requests ready at the same time. One request is on the workflow's critical path and unlocks downstream work; the other is independent. In baseline mode, they are treated equally or run in arrival order. In controller mode, the harness marks the critical-path request, so the backend runs it first and downstream work can start earlier.

In simple words: the backend should prepare before a replay arrives, using what the harness already knows, instead of waiting until the user is already waiting.

How the experiment is set up

Combine the key lifecycle facts in one small workflow: a target session enters tool wait, has valuable reusable KV, and has a known replay deadline. Add background pressure during the wait. In baseline mode, the backend reacts only after replay arrives. In controller mode, the backend uses the harness signals to prepare KV, priority, and capacity before the replay shows up.
