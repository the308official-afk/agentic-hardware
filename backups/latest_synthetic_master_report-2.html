Executive Summary

This report is designed to answer two different questions without mixing them together.

  • The clean run is the performance source of truth because it runs without torch.profiler overhead.
  • The mechanism run is the movement source of truth because it exposes lightweight SGLang KV-copy telemetry, with torch-profiler CUDA HtoD as optional validation.

Experiment Setup And Manager Summary

This section is intended for slide-building. It explains how the controlled synthetic experiment was set up, what was measured, and how to read the hardware motivation.

Simple Setup

part simple meaning example
1. Request source Synthetic agent sessions create controlled model turns. synthetic task -> initial SGLang model request
2. Tool wait window The driver inserts a controlled pause. That pause is the chance to prefetch KV. emulated read_file(), grep(), or run_tests() wait
3. Resume request The replay turn arrives, and we measure whether KV was ready before first token generation. tool result arrives -> replay prompt starts

Modes Compared

mode what happens
No prefetch The system waits until replay arrives, then SGLang handles KV reuse/load normally.
Prefetch modes During the tool wait, request-warm/direct-load/oracle modes try to prepare KV before replay.

What Was Measured

metric meaning
replay TTFT Time from replay admission to first generated token in the clean run.
prefetch margin Whether the copy/hint path finished before or after replay was due.
KV copy ready Whether SGLang-level KV-copy telemetry finished before replay.
CUDA HtoD ready Whether torch-profiler CUDA host-to-device copy evidence finished before replay.
replay reloaded KV Whether the replay still triggered SGLang KV load-back work even after a hint.

What Was Observed

observation evidence
The synthetic setup gives controlled stress conditions. We can make tool waits short, add cache pressure, and choose prefetch timing deliberately.
Performance and attribution are intentionally separated. Clean runs support TTFT claims; profiled runs support DMA/KV mechanism claims.
The current best clean mode is recorded in the report. Best non-baseline mode shown here: oracle_direct_load.
The mechanism run shows whether KV movement was actually visible. CUDA HtoD visible sessions: 3 / 6.
Replay reload behavior is a key failure signal. Replay reloaded KV in 6 / 6 profiled sessions.

Why This Supports The Hardware Proposal

The synthetic setup lets us stress the exact failure modes we care about: short tool gaps, cache pressure, late prefetch, replay reloads, and unclear residency. If a software hint path copies or loads KV too late, or if replay reloads KV anyway, that supports the need for deadline-aware KV movement, residency protection, and better hardware/runtime telemetry.

One Row In Plain English

Each timeline row is one tool-wait episode: model turn, tool call, wait, optional prefetch, then model resume.

step timeline color simple meaning
1. Ask model what to do blue bar model turn before the tool call
2. Model says to call a tool end of blue bar the model turn hands work to a tool
3. Tool runs gray bar the synthetic tool wait is happening
4. Agent waits gray bar this wait is the prefetch opportunity
5. Tool returns black vertical line the next model turn is due
6. Agent asks model again red bar resume request after the tool result
During steps 3/4, if prefetch is enabled purple bar our prefetch/direct-load attempt runs during the wait

Color Legend

color meaning simple description
blue Initial model turn The agent asks the model what to do next. In the synthetic report, this is the first request before the simulated tool wait.
gray Tool wait window The tool is assumed to be running, so the model is idle for this session. This pause is the opportunity to prepare that session's KV before the agent resumes.
purple Prefetch attempt window This includes detecting the tool-wait opportunity, creating a hint for that agent/session, calling our direct SGLang KV hook, letting SGLang check whether host-side KV exists, and if needed, asking SGLang to move KV back to GPU memory.
green KV copy/load activity This is evidence that KV load/copy work was observed for the hint. Dark green is CUDA HtoD profiler evidence; light green is lightweight SGLang KV telemetry fallback.
black Replay due boundary This is when the tool result is ready and the next model turn should be able to start. If purple or green finishes after this line, the prefetch path was late for that resume.
red Replay request The agent asks the model to continue after the tool result. This is the request we want to speed up by having the right KV ready before it arrives.
yellow First token marker This marks when the replay request starts producing output. It helps separate request arrival from first-token latency.

Key Deductions

  • We should judge TTFT using the clean run, then use the profiled run to explain why the result happened.
  • Some hint paths did not fully finish before replay. That supports the concern that software hints can be delayed by the normal serving path.
  • 6 paired sessions show replay reload behavior, which is the exact failure mode eviction protection/residency hints are meant to address.

Timeline Layers

Layer Meaning Why it matters
gray tool_wait The agent is waiting for a tool result, such as tests, search, or build output. This is the opportunity window where prefetch can happen before the next model turn.
purple hint_request The software request we currently send to SGLang to trigger KV load-back. This is not pure DMA. It includes scheduling, prefix matching, KV load-back, model work, and request bookkeeping.
green copy activity The single visible KV copy-activity bar. Dark green is used when CUDA HtoD profiler evidence exists. Light green is used as a fallback when only lightweight SGLang KV telemetry exists. This keeps the main chart simple while preserving the exact telemetry and torch timings in the tables.
red replay The real agent replay request. If the purple hint request overlaps the red replay in time, the prefetch path was still running when the agent needed to resume.
black replay_due The time when the tool result is ready and the real replay request is due. If prefetch finishes after this line, the agent can still stall waiting for KV.
green/red dashed gap The time between KV/copy completion and replay due. Green means KV movement finished before replay. Red means replay was already due before movement finished.

Prefetch Checkpoints

Checkpoint Simple meaning Why it matters
KV copy ready before replay The lightweight green KV-copy telemetry ended before the black replay-due line. This is the scalable checkpoint for larger runs where torch.profiler is off.
CUDA copy ready before replay The dark-green profiler HtoD copy ended before the black replay-due line. This proves profiler-visible GPU copy work happened early enough, but only for the copied slice we attributed in smaller validation runs.
Full hint done before replay The whole purple hint request finished before replay resumed. This catches cases where the copy started early but the normal SGLang request path was still busy.
Replay reloaded KV The real replay request still triggered SGLang KV load-back events. This catches cases where prefetched KV was incomplete, evicted, or not enough for the replay.
